# Проект схемы данных: Части 2 и 3

Это проект логической схемы для Частей 2 и 3 [BACKEND_MVP_TZ.md](./BACKEND_MVP_TZ.md), включая границу биллинга на уровне аккаунта из Части 2.5 и canonical пользователей из Части 3. ТЗ остаётся главным источником требований. Пункты, помеченные как предложения, — варианты реализации там, где ТЗ не задаёт техническое правило; это не новые требования к поведению продукта.

## 1. Владение данными и изоляция

Иерархия владения: `account -> project -> agent`. Membership, роли и entitlements принадлежат аккаунту. Каналы, настройки агента, каталог, база знаний, клиенты, диалоги, заявки и эскалации принадлежат проекту. Доступ проверяется по JWT scope, членству в аккаунте и связи проекта с этим аккаунтом, как указано в ТЗ и [core-architecture.md](./core-architecture.md).

В каждой таблице с проектными данными хранится обязательный `project_id`, ссылающийся на `projects.id`, в том числе в дочерних записях, у которых проект можно определить через родителя. Каждый запрос проектных данных ограничивается контекстом проекта пользователя. Для ссылок между проектными записями используются составные внешние ключи с `project_id`, чтобы запись не могла ссылаться на родителя из другого проекта. Для таких внешних ключей родительским таблицам потребуются соответствующие уникальные ключи, например `(project_id, id)`.

`projects.account_id` ссылается на `accounts.id`. В аккаунтных записях хранится `account_id`; в записях, которые относятся к проекту, но учитываются или оплачиваются на уровне аккаунта, хранятся оба идентификатора — `account_id` и `project_id`. Предлагаемый способ гарантировать их согласованность — составной внешний ключ на `(projects.id, projects.account_id)`.

`accounts.id` и `users.id` — canonical backend IDs. Внешние идентификаторы аккаунтов и пользователей хранятся в отдельных таблицах `account_identities` и `user_identities`; в каждой уникальна пара `(identity_provider, external_*_id)`, а несколько external IDs могут ссылаться на один backend ID, когда recovery инициирован от этого canonical backend ID. Прежняя `accounts.external_id` переносится в `account_identities` как Bitrix external UUID и удаляется; миграция останавливается, если значение не соответствует формату UUID.

`account_memberships.user_id` ссылается на canonical пользователя в `users.id` (`ON DELETE RESTRICT`). Таблица `users` хранит минимальный профиль без ПДн: backend-generated `id` (`Text`), `created_at` и `updated_at`. Статус не хранится в `users`: отключение выполняется на уровне membership. `user_identities.user_id` также ссылается на `users.id` (`ON DELETE RESTRICT`). Миграция переносит существующие membership IDs в `users`, не меняя их; найденные старые `audit_log.actor_id` импортируются как users, чтобы сохранить ссылки аудита.

В Bitrix JWT claim `sub` содержит immutable внешний UUID пользователя и разрешается через `user_identities`; в membership и аудит передаётся canonical backend `user_id`. Auth flow проверяет RS256/key `kid`, claims и scopes, затем читает актуальную роль из active membership. Полный runtime flow и состав principal описаны в разделе 8; дополнительная сущность или таблица БД для principal не вводится. Аутентифицированный автор аудита — nullable FK `audit_log.actor_id → users.id`; системный автор хранится отдельно в `system_actor`. Одновременно задавать оба поля запрещено.

Управление membership выполняется доменными сервисами `membership_service.py`. Статус membership (`active`/`disabled`) задаёт доступ пользователя к аккаунту; owner отключить нельзя (check `ck_account_memberships_owner_active`). Назначение operator на проект хранится в `project_operators` и тоже может быть отключено. Роли определяются матрицей `access_policy.py`: owner управляет только ролями admin и operator, admin управляет только operator, operator не управляет membership. В аккаунте ровно один owner — его создатель; роль owner не назначается, не понижается и не удаляется через доменные сервисы membership, она задаётся только provisioning. Роль актора всегда читается из `account_memberships` в текущей транзакции. Обычный provisioning создаёт backend IDs, оба mapping и membership owner; повтор с тем же external ID не создаёт дубликаты и не перепривязывает внешний ID. При восстановлении backend ID является источником истины: новые Bitrix external IDs связываются с переданными существующими backend IDs отдельными reconciliation-сервисами; поиск по email/имени и автоматический merge запрещены, конфликт уже занятого external ID завершается ошибкой. Каждое изменение membership пишет `audit_log` с системным или аутентифицированным автором и только идентификаторами и ролями в `diff`.

## 2. Сущности и связи

| Сущность или группа | Владение / ключи изоляции | Связи |
|---|---|---|
| `accounts` | Корневая сущность аккаунта | На неё ссылаются `projects` и аккаунтные записи. |
| `account_identities` | Глобальная: `account_id` | Сопоставляет `(identity_provider, external_account_id)` с canonical `accounts.id`; одному аккаунту могут соответствовать несколько подтверждённых внешних identities. |
| `users` | Глобальная: `id` | Canonical пользователи без ПДн; используются членством аккаунта, внешними identity mappings и аудитом. Статуса пользователя нет. |
| `user_identities` | Глобальная: `user_id` | Сопоставляет `(identity_provider, external_user_id)` с canonical `users.id`; одному пользователю могут соответствовать несколько подтверждённых внешних identities. |
| `account_memberships` | Аккаунт: `account_id`, пользователь: `user_id` | Каждая запись принадлежит аккаунту и пользователю. `user_id -> users.id` (`RESTRICT`); уникальность `(account_id, user_id)`; разрешённые роли `owner`/`admin`/`operator`; `status` (`active`/`disabled`, по умолчанию `active`); не более одного owner на аккаунт (частичный уникальный индекс `uq_account_memberships_one_owner`); owner не может быть `disabled`. |
| `project_operators` | Аккаунт, проект, membership | Проектный roster operator: `account_id`, `project_id`, `membership_id`, `status` (`active`/`disabled`). Составные FK `(project_id, account_id)` и `(membership_id, account_id)` (`RESTRICT`); уникальность `(project_id, membership_id)`. Само включение в roster не даёт доступа к диалогам. |
| `dialog_operator_assignments` | Аккаунт, проект, диалог, membership | Текущее назначение одного оператора на диалог. `session_id` — PK, `membership_id` уникален: один диалог на оператора и один оператор на диалог. Составные FK связывают проект/аккаунт, диалог/проект и membership/аккаунт (`RESTRICT`). Назначение создаётся только для активного operator-membership в активном roster проекта; при освобождении, разрешении эскалации или отключении оператора удаляется. |
| `entitlements` | Аккаунт: `account_id`, одна запись на аккаунт | Вычисленный snapshot/cache прав из `Subscription.snapshot`, доступного баланса и `agent_slots`, хранящийся в БД с TTL 60 секунд. Изменения подписки, баланса, тарифа и слотов инвалидируют snapshot триггерами в той же транзакции; изменение текущей версии тарифа не меняет оплаченные права. Флаги и квоты отражают эффективные права; таблица не является самостоятельным источником прав. |
| `projects` | Проект принадлежит аккаунту: `account_id` | `account_id -> accounts.id`; индекс по `account_id`. |
| `agents`, `agent_drafts`, `agent_releases` | Проект: `project_id` | Агент принадлежит проекту; draft и неизменяемые releases — агенту в том же проекте. До первой публикации `active_release_id` может быть пустым; иначе он должен указывать на release того же агента. Версия уникальна в пределах агента. Draft хранит изменяемый JSONB `config`; release — неизменяемый JSONB `snapshot` с ключами `prompt`, `tone`, `model_settings`, `sales_rules`, `functions`, `response_settings`. Credentials канала, каталог и база знаний в snapshot не включаются. |
| `channels` | Проект: `project_id` | Канал принадлежит проекту. Идентификатор подключения уникален согласно контракту интеграции. |
| `catalog_sources` | Проект: `project_id` | Источник принадлежит проекту; в MVP-1 допускается не более одного авторитетного источника. При замене старый источник деактивируется, история импортов и товаров сохраняется. |
| `catalog_imports`, `catalog_import_errors` | Проект: `project_id` | Импорт ссылается на источник того же проекта; ошибки импорта принадлежат импорту того же проекта. |
| `products` | Проект: `project_id` | Товар принадлежит источнику каталога и может ссылаться на импорт, в котором его видели в последний раз; все ссылки — в рамках того же проекта. |
| `kb_documents`, `kb_chunks` | Проект: `project_id` | Chunk принадлежит документу того же проекта; идентификаторы vector points относятся к производным данным в Qdrant. |
| `customers`, `customer_identities`, `customer_variables` | Проект: `project_id` | Identity и переменные клиента принадлежат клиенту в том же проекте. Неподтверждённые контактные значения не используются для объединения identity. |
| `chat_sessions`, `chat_messages`, `dialog_variables` | Проект: `project_id` | Сессия связана с проектом, каналом и клиентом этого проекта. Сообщения и переменные диалога принадлежат сессии того же проекта. При возобновлении закрытой сессии сохраняются та же строка и `release_id`. Для `(project_id, channel_id, external_chat_id)` допускается не более одной активной сессии. |
| `tool_executions` | Проект: `project_id` | Ссылается на сессию и, если есть, сообщение того же проекта. Аргументы и результаты редактируются; credentials исключаются. |
| `leads`, `lead_items` | Проект: `project_id` | Заявка ссылается на проект, сессию и клиента; её позиции принадлежат заявке и сохраняют подтверждённый снимок товара. |
| `escalations` | Аккаунт и проект: `account_id`, `project_id` | Ссылается на сессию этого проекта. `assignee_membership_id` — nullable FK на текущего оператора того же аккаунта; открытая эскалация согласована с текущим назначением диалога. При освобождении или разрешении эскалации назначение очищается; аудит хранит canonical `user_id`. Частичный уникальный индекс допускает не более одной эскалации со статусом `open` на диалог. Статусы не ограничены enum/CHECK; доменный сервис использует `open` и `resolved`. |
| `inbox` | Проект: `project_id` | Ссылается на канал этого проекта; идентификатор события провайдера уникален в рамках канала. |
| `background_jobs` | Задачи проекта: обязательный `project_id` | Каждая задача приложения относится к проекту; ссылки из payload разрешаются в том же проекте. Общесистемные задачи без проекта в эту схему не входят. |
| `outbox` | Проект: `project_id` | Ссылается на проект и его канал/aggregate. Перед созданием проверяется актуальный session fence. |
| `events`, `audit_log` | Контекстные: `account_id`, а для проектных событий также `project_id` | Проектное событие указывает проект; аккаунтное действие — аккаунт. Требуются индексы по проекту/времени/типу, retention и маскирование ПДн. |
| `llm_calls`, `usage_counters` | Контекст аккаунта и проекта | Для проектного использования хранят `account_id` и `project_id`; нужны индексы для запросов по времени. Credentials провайдера не хранятся. |
| `tariff_plans`, `llm_models`, `dancoin_packages` | Глобальные версионируемые каталоги | На них ссылаются биллинг и учёт использования; они не принадлежат проекту. |
| `subscriptions` | Аккаунт: `account_id` | Ссылается на `accounts` и `tariff_plans`; не более одной текущей подписки на аккаунт; trial выдаётся аккаунту один раз. По окончании оплаченного периода и при ручной отмене платные LLM-вызовы немедленно прекращаются; 7-дневный grace period предназначен только для оплаты/возобновления и сохранения конфигурации, затем аккаунт переходит в `parking`. |
| `dancoin_balances` | Аккаунт: `account_id` | Связь один-к-одному с `accounts`; ledger — источник финансовой истины, баланс — атомарная проекция раздельных грантового/купленного остатков, резервов и долга. Ежедневная сверка восстанавливает проекцию из ledger и активных reservations и создаёт alert; ledger не переписывается. |
| `dancoin_transactions`, `dancoin_reservations` | Аккаунт: `account_id` | Transactions — неизменяемый ledger; reservation указывает аккаунт и операцию/call. Резервирование атомарно проверяется против доступного баланса аккаунта. Исправление проводится компенсирующей записью, а не изменением существующей. Расходование использует гранты первыми; долг от поздней корректировки погашается только купленными Dancoin, начисления покупок сначала закрывают долг, гранты долг не уменьшают. Долг блокирует платные LLM-вызовы. |
| `invoices`, `payments`, `payment_events` | Аккаунт: `account_id` | Invoice принадлежит аккаунту; payment ссылается на invoice того же аккаунта; payment event связан с аккаунтом через payment/invoice. Повторное уведомление дедуплицируется по `provider_event_id`; финансовый эффект имеет отдельную идемпотентность по payment/invoice. Статус платежа подтверждается через provider adapter. |
| `usage_records` | Смешанный scope: `account_id`, `project_id` | Одна неизменяемая запись на биллинговую операцию: `id`, `account_id`, optional `project_id`, `metric`, `quantity`, `unit`, optional token counts, `model_id`, `price_version`, `dancoin_cost NUMERIC(12,2)`, UTC billing period, `occurred_at`, unique `idempotency_key`. Для `llm_calls` `project_id` обязателен; запись проекта относится к аккаунту-владельцу. Корректировки — новыми связанными записями. `usage_counters` — агрегаты по проекту, периоду и метрике, не взаимозаменяемы с фактами; usage, агрегат и ledger settlement атомарны. |
| `agent_slots` | Проект: `project_id` | Одна запись на проект; лимиты слотов атомарно проверяются и обновляются для проекта. Подписка и баланс Dancoin общие для аккаунта. |

Таким образом, в Части 2.5 есть три scope: глобальные версионируемые каталоги (`tariff_plans`, `llm_models`, `dancoin_packages`), аккаунтные записи подписок/платежей/Dancoin и проектные лимиты агентов с атрибуцией использования. `usage_records` имеют смешанный scope: оплата относится к аккаунту, а `project_id` показывает, в каком проекте возникло использование.

### 2.1. Биллинговые контракты

- **Snapshots:** invoice хранит JSONB snapshot с `schema_version`, `purchase_type`, `catalog_item` (`id`, `code`, `version`, `name`) и `price` (`amount` десятичной строкой, `currency`). Тарифный snapshot также фиксирует период, `features`, `limits`, `dancoin_grant_conditions` и применённую сумму гранта; snapshot пакета фиксирует количество Dancoin. При успешной оплате subscription получает snapshot условий invoice на оплаченный период и ссылку на invoice. Новые версии каталога не изменяют ранее созданные snapshots.
- **Источники истины:** опубликованные версии каталогов, snapshots invoice/оплаченного периода и неизменяемый Dancoin ledger. `dancoin_balances` — атомарная проекция ledger и активных reservations с раздельными грантовым/купленным остатками, резервами и долгом. `dancoin_transactions.balance_after` — доступный для новой траты остаток после операции: `0`, если `debt_balance > 0`, иначе `max(0, grant_balance + purchased_balance - reserved_grant - reserved_purchased)`. `entitlements` — вычисляемый snapshot/cache прав из тарифа, состояния подписки, доступного баланса и `agent_slots`; он не является источником каталожных условий.
- **Платёжные события:** событие сначала сохраняется в `payment_events` со статусом `received`, затем проверяется через адаптер провайдера и применяется транзакционно. Дедупликация уведомлений выполняется по `(provider, provider_event_id)`; сумма, валюта и invoice в подтверждении должны совпадать с локальными payment и invoice, иначе событие отклоняется без финансового эффекта. Первый подтверждённый платёж за invoice/период применяет его эффект один раз; поздний второй успешный платёж не продлевает подписку и не начисляет Dancoin повторно, а автоматически возвращается через адаптер провайдера. Успешная оплата нового invoice возобновляет подписку из его snapshot, в том числе после истечения периода или отмены; старые события не откатывают уже применённую оплату.
- **Idempotency invoice/payment:** каждый invoice и payment создаётся с обязательным непустым `idempotency_key`, уникальным в пределах аккаунта; сервисы проверяют ключ до записи, а БД запрещает `NULL` и дубли.
- **Расчёт и учёт LLM usage:** ставки читаются по точной паре `(model_id, price_version)`. Если `input_tokens > long_context_threshold_tokens`, для обоих направлений токенов применяются long-context ставки; при равенстве порогу применяются базовые ставки. `dancoin_cost = ceil(((input_tokens * input_price_per_1k + output_tokens * output_price_per_1k) / 1000) * 100) / 100`, вычисление выполняется в `Decimal`, итог округляется вверх до `0.01`. Для каждого LLM-вызова создаётся одна неизменяемая `usage_records` запись с `metric='llm_calls'`, `quantity=1`, `unit='call'`, токенами и стоимостью; её `idempotency_key` совпадает с reservation `operation_id`. `usage_counters.value` — сумма `quantity` по `(project_id, period_start, metric)`: для LLM-вызовов увеличивается на `1`, не на число токенов или Dancoin. Запись факта, upsert агрегата и settlement (или поздняя корректировка timeout charge) выполняются в одной транзакции.
- **Entitlements Engine:** `entitlements.snapshot` кэширует эффективные права на 60 секунд; триггеры в той же транзакции инвалидируют snapshot при изменении `subscriptions`, `dancoin_balances`, используемого `tariff_plans` или `agent_slots`. Инвалидация ставит `expires_at = to_timestamp(0)` (миграция `20261203_entitlement_invalidate`), а не время БД: сервис сравнивает `expires_at` с часами приложения, и рассинхронизация часов не должна скрывать инвалидацию. Условия тарифа для оплаченного периода читаются из `Subscription.snapshot` (созданного из invoice snapshot), а не из изменяемой строки каталога; для legacy snapshots, не содержащих `included_agents`/`max_agents`, эти два поля берутся из закреплённой версии тарифа. `features` в subscription snapshot содержит boolean-ключи `llm_calls_enabled`, `catalog_import_enabled`, `knowledge_base_enabled`, `multi_channel_enabled`; отсутствующий ключ означает `false`. `limits` содержит целочисленные квоты `max_projects`, `max_catalog_sources_per_project`, `max_products_per_project`, `max_kb_documents_per_project`; отсутствующая/null-квота означает отсутствие лимита. `included_agents`/`max_agents` — отдельные поля snapshot тарифа; extra-agent сверх включённого лимита не допускается, пока цена не утверждена. LLM-доступ требует `trial`/`active` подписку в пределах периода, включённый feature и положительный доступный баланс; окончательную достаточность средств проверяет атомарный reservation. `grace_period` допускает только оплату и конфигурацию до `grace_until`; `parking`/отмена не дают платного доступа. При `agent_create` проверка и инкремент `used_slots` сериализуются в транзакции; освобождение агента уменьшает счётчик в транзакции.
- **Транзакционные границы:** ledger-операция и balance-проекция обновляются вместе под блокировкой аккаунта; сервисные операции Dancoin требуют активной транзакции, а commit/rollback контролирует вызывающий слой, чтобы объединить settlement с `usage_records` и `usage_counters`. Handoff проверяет `llm_call` entitlement и резервирует переданный вызывающей стороной `maximum_cost` в одной транзакции. Затем провайдер вызывается без открытой транзакции, а token usage, usage counter и settlement фиксируются атомарно в новой транзакции; settlement освобождает неиспользованный остаток резерва. Контракт провайдера возвращает результат и фактические input/output token counts отдельно от `dialog.ModelTurn`. Вызывающая сторона отвечает за корректную пару `model_id`/`price_version` и ценовой максимум; коммерческие лимиты и значения не задаются handoff-сервисом. Известную ошибку вызова адаптер сообщает как `LLMProviderCallError`; handoff тогда освобождает reservation и повторно поднимает ошибку. Ошибка записи usage после успешного ответа оставляет reservation для повторной фиксации или штатного timeout/reconciliation, а не освобождает уже потреблённый вызов. Сетевой LLM-вызов выполняется вне открытой БД-транзакции: reservation фиксируется заранее отдельной транзакцией. Payment event сохраняется в durable inbox до ACK; подтверждённый и идемпотентный финансовый эффект применяется транзакционно. Ежедневная сверка восстанавливает только balance-проекцию по ledger и активным reservations; ledger не редактируется.
- Конкретные цены, валюты, гранты и лимиты остаются продуктовыми данными и не задаются миграциями до утверждения; поля snapshots описывают структуру, но не значения прайса.

#### Формулы задолженности Dancoin

Все суммы выражаются в Dancoin с точностью `0.01`. Обозначим текущий долг как `D`, купленное начисление как `P`, возврат как `R`, сумму timeout charge как `M`, а позднюю фактическую стоимость как `A`.

- **Погашение долга купленным начислением:** `debt_repaid = min(P, D)`; `debt_balance_new = D - debt_repaid = max(0, D - P)`; `purchased_balance_new = purchased_balance + P - debt_repaid`. Грантовое начисление долг не погашает. Возврат из купленного источника следует той же формуле с `R` вместо `P`; возврат грантовой суммы не меняет долг.
- **Поздняя стоимость меньше timeout charge (`A < M`):** неиспользованная сумма возвращается в соответствующие buckets резерва. Грантовый возврат долг не погашает. Купленный возврат сначала уменьшает долг: `debt_repaid = min(D, purchased_refund)` и `debt_balance_new = D - debt_repaid`; остаток `purchased_refund - debt_repaid` зачисляется в `purchased_balance`.
- **Поздняя стоимость больше timeout charge (`A > M`):** `extra_charge = A - M`. Доплата списывает доступные гранты первыми, затем купленные Dancoin: `grant_charge = min(extra_charge, grant_balance - reserved_grant)`; `purchased_charge = min(extra_charge - grant_charge, purchased_balance - reserved_purchased)`. Непокрытая часть становится долгом: `shortfall = extra_charge - grant_charge - purchased_charge`; `debt_balance_new = D + shortfall`. Если `A = M`, корректирующая запись не требуется.
- **Ограничение расходов:** при `debt_balance > 0` доступный остаток для новых расходов и reservations равен нулю; после погашения долга он вычисляется как `max(0, grant_balance + purchased_balance - reserved_grant - reserved_purchased)`.

### Каталог, клиенты и база знаний

Все новые записи содержат `project_id`. Ссылки между источниками и импортами, импортами и ошибками, источниками и товарами, товарами и последним импортом, клиентами и identities, документами и chunks используют составные внешние ключи с `project_id`.

`catalog_sources.mapping`, `products.attributes` и `customers.profile` — JSONB для гибких структур. Остальные поля, нужные для уникальности, фильтрации и сортировки, хранятся явно. `catalog_sources` допускает один авторитетный источник на проект через частичный уникальный индекс.

Финализация импорта выполняется одной транзакцией: блокирует запись импорта и источника, upsert-ит товары, помечает отсутствующие товары неактивными и обновляет статус импорта. Деактивация разрешена только после полного чтения и обработки файла без структурных ошибок, с безопасным отчётом полноты и без completeness-critical ошибок. При любой ошибке SQL вся транзакция откатывается; некритичные ошибки строк могут завершить импорт со статусом `completed_with_errors`.

`kb_documents` хранит исходный ключ, имя файла, текст (если доступен), версию и статус обработки. `kb_chunks` хранит текстовые фрагменты и внешний `vector_id`; сами embeddings остаются в Qdrant. Уникальность chunk обеспечивается в рамках документа и его версии.

Значения статусов, типы и длины отдельных полей в новых таблицах — решения реализации там, где они не зафиксированы ТЗ; проверяемые им ограничения и индексы описаны в соответствующей Alembic-миграции и интеграционных тестах.

### Прикладные события, доставка и диагностика

`inbox` сохраняет статус очереди, время получения и завершения, безопасную диагностику ошибки и нормализованное событие. Повторная доставка дедуплицируется по `(project_id, channel_id, provider_event_id)`; создание события и фоновой задачи выполняется в транзакции вызывающей стороны.

`background_jobs` хранит приоритет, lease, попытки, следующее время запуска (`available_at`), correlation ID и диагностическую ошибку. Выдача задач использует `FOR UPDATE SKIP LOCKED`; повторные попытки выполняются с ограниченным backoff, а ключ идемпотентности защищает enqueue от дублей. Для внешних вызовов exactly-once не обещается.

`outbox` хранит вид сообщения, destination, aggregate ID, payload, idempotency key, попытки, deadline, следующее время доставки (`available_at`) и причину удержания/неопределённого результата. `enqueue_outbound_message` проверяет актуальный session fence в той же транзакции, что и запись Outbox и durable job. `commit_turn` также проверяет fence перед фиксацией сообщений, событий и Outbox.

`domain_events` — неизменяемый журнал событий; для выборки добавлен индекс по проекту, времени и типу. `tool_executions` ссылается на сессию и, при наличии, сообщение того же проекта. `leads` и `lead_items` используют project-scoped ссылки, уникальный ключ заявки и снимок подтверждённого товара. `escalations` индексируется по проекту, статусу и SLA deadline. `audit_log` содержит account/project context, автора, действие, сущность и очищенный diff. `llm_calls` хранит provider/model/purpose, токены, задержку и код ошибки без provider credentials; `usage_counters` агрегирует метрики по проекту и периоду.

Для JSONB payload и диагностических текстовых полей persistence-слой маскирует распознаваемые credential-поля/значения перед записью. В `domain_events.payload` и `audit_log.diff` дополнительно маскируются распознаваемые адреса email и телефонные номера. `audit_log.diff` ограничен allowlist полей для каждого действия; неподдерживаемые действия, ключи и нетекстовые значения отклоняются до записи. Структурированное логирование редактирует известные секреты из настроек и окружения, а также распознаваемые email и телефонные номера в сообщениях и трассировках. ## 4. Архивация и удаление проекта

При запросе удаления проект сразу архивируется. Все данные проекта, включая PostgreSQL-записи и Qdrant points, остаются недоступными для обычной работы и хранятся не менее 30 дней, чтобы tenant мог восстановить проект. Восстановление в течение 30 дней отменяет ожидающее удаление и возвращает прежний статус проекта. Если данные проекта создавались или изменялись в последние 30 дней перед purge, физическое удаление откладывается до истечения 30 дней без активности.

1. Удаление аккаунта **запрещено (`RESTRICT`)**, пока на него ссылаются проекты, текущие подписки, invoices/payments, ledger или записи с обязательным сроком хранения. Удаление аккаунта — отдельная операция жизненного цикла, а не массовый каскад.
2. При физическом удалении проекта дочерние PostgreSQL-записи удаляются внутренней процедурой в порядке внешних ключей. Текущие project FK используют `RESTRICT`, поэтому порядок очистки проверяется интеграционным тестом.
3. `domain_events`, `audit_log`, `llm_calls` и `usage_counters` хранятся вместе со всем архивом до окончательного удаления проекта.
4. Когда истекли 30 дней с запроса удаления и не было создания/изменения данных проекта в течение последних 30 дней, удаляются Qdrant points из одной конфигурируемой коллекции по фильтру с `project_id` и `object_type` (`kb_chunk` или `product`). Для Qdrant нет SQL FK. Сбой внешней очистки нельзя считать успешным завершением удаления проекта.
5. После выполнения обоих условий отдельная ежедневная команда удаляет все project-scoped записи и корневую запись проекта в порядке внешних ключей. Повторный запуск процедуры удаления должен быть безопасным. Активность проверяется по временным меткам всех удаляемых таблиц и самого проекта; lifecycle-запись запроса удаления не считается активностью данных проекта.
6. Диагностические записи `catalog_import_errors` для проектов, не ожидающих удаления, очищаются после 30 дней. Это не удаляет импортированный каталог, продукты или Qdrant points активного проекта.

Порядок очистки принят: сначала Qdrant, затем PostgreSQL. В текущей схеме project FK используют `RESTRICT`; сервис удаляет дочерние строки явно в порядке зависимостей. Восстановление возможно в течение первых 30 дней; purge может быть отложен дольше, если в данных проекта была недавняя активность. Новые временные поля существующих строк заполняются временем миграции, что консервативно откладывает их purge до истечения окна активности. Защищённые API endpoints архивации/удаления и восстановления будут реализованы после появления общей авторизации. Команда: `uv run --no-sync python -m ai_seller_core.jobs.project_deletion_scheduler`; она запускается ежедневно через системный scheduler/cron, не через worker.

## 5. Инварианты транзакций и конкурентного доступа

- `commit_turn` — единственная транзакционная точка записи результата диалогового хода: блокировка сессии, проверка владельца lease/fence, затем атомарная запись сообщений, изменений сессии, доменных событий и Outbox. При ошибке проверки все записи откатываются.
- Открытие/возобновление и закрытие сессии выполняются Dialog Worker в отдельных коротких транзакциях с блокировкой и аудитом. Закрытый диалог возобновляется в той же строке, с прежней историей и `release_id`.
- Вызовы LLM, мессенджера, Qdrant и файлового хранилища не выполняются внутри долгих бизнес-транзакций.
- Для фоновых задач используется доставка at-least-once и идемпотентная обработка, с lease/retry-метаданными, `job_id`, `correlation_id` и ограниченной безопасной диагностикой. Exactly-once для внешних HTTP-вызовов не обещается.
- Публикация release блокирует строку агента, проверяет draft, создаёт неизменяемый release и переключает `active_release_id` в одной транзакции. Создание сессии блокирует ту же строку агента на чтение статуса/release и запись сессии. Откат атомарно переключает указатель, не изменяя release.
- Счётчики/лимиты проекта и резервирование аккаунтного баланса изменяются атомарно при конкурентном доступе.

## 6. Текущее состояние реализации

Модели и миграции persistence покрывают аккаунты и проекты, canonical пользователей (`users`, `user_identities`) и membership, каналы, конфигурации агентов и релизы, диалоги, каталог, клиентов и базу знаний, Inbox/Jobs/Outbox, прикладные сущности, события, аудит с FK на пользователя или отдельным системным actor, вызовы LLM, счётчики использования и запросы удаления проектов. Проектные связи и ограничения изоляции задаются внешними ключами, включая составные связи с каналом и сессией. Реализация проверок lease/fence, атомарной фиксации хода, идемпотентности и безопасного удаления описана в соответствующих разделах ниже. Наличие persistence-модели не означает, что для каждой сущности уже реализованы публичные API и внешний runtime.

Схема и миграции отражают реализованную persistence-основу. Публичные API, внешние интеграции и отдельные runtime-сценарии могут оставаться задачами последующих частей.

### API foundation — Часть 4 (реализовано частично)

В `create_app()` подключён версионированный router `/api/v1`. Реализованы:

| Method | Path | Назначение |
|---|---|---|
| `GET` | `/api/v1/account` | Текущий account по principal |
| `GET`, `POST` | `/api/v1/account/members` | Список и добавление membership |
| `PATCH`, `DELETE` | `/api/v1/account/members/{user_id}` | Изменение роли/статуса и удаление membership |
| `POST` | `/api/v1/internal/onboarding/accounts` | Server-to-server provisioning account, user, identity и owner membership |
| `GET`, `POST` | `/api/v1/projects` | Список и создание проектов |
| `GET`, `PATCH`, `DELETE` | `/api/v1/projects/{project_id}` | Чтение, изменение и запрос удаления проекта |
| `POST` | `/api/v1/projects/{project_id}/archive` | Архивация проекта с retention-запросом |
| `POST` | `/api/v1/projects/{project_id}/restore` | Восстановление проекта |
| `GET`, `POST` | `/api/v1/projects/{project_id}/agent` | Чтение и создание одного агента проекта |
| `PATCH` | `/api/v1/projects/{project_id}/agent/draft` | Сохранение черновика агента |
| `POST` | `/api/v1/projects/{project_id}/agent/publish` | Создание release snapshot |
| `POST` | `/api/v1/projects/{project_id}/agent/rollback` | Переключение active release |

Маршруты используют request-scoped DB-сессию и типизированный `Principal`/scopes. Роли, проверка tenant ownership и операции membership/project/agent остаются в persistence services; DTO проектов не раскрывают `Project.settings`. Список account members ограничен `owner`/`admin`. Onboarding защищён отдельным `ONBOARDING_SERVER_CREDENTIAL` (не менее 32 символов) и не использует пользовательский JWT. Создание проекта проверяет активную подписку и `max_projects`; изменение настроек проекта и agent draft/release проверяют `configuration` entitlement (активная подписка или configuration grace period). Agent create атомарно проверяет Entitlements Engine и резервирует `agent_slots`; project purge удаляет принадлежащую проекту строку слота.

Для повторяемых изменений используется `Idempotency-Key` (до 200 символов). Таблица `api_idempotency_records` хранит хэши ключа и тела, JSON-ответ и `expires_at`; одинаковый ключ/тело повторно выдаёт сохранённый результат, другое тело даёт `409`. Срок хранения — 30 дней; просроченные записи удаляются функцией retention scheduler и при повторном обращении с истёкшим ключом.

Для API зарегистрирован общий error envelope. Доменные ошибки auth/authorization/not-found/conflict/agent-config validation отображаются как `401`/`403`/`404`/`409`/`422`; entitlement errors сохраняют доменные `402`/`403`/`404` и код ошибки. Отсутствующая конфигурация onboarding отвечает `503`.

Окончательный project purge работает fail-closed: если Qdrant не настроен, retention-запрос остаётся `pending` (чтобы не оставить vector points без владельца); завершить его можно после подключения vector store. Проверки API выполняются с fake DB dependency; отдельные PostgreSQL-тесты проверяют миграции, agent entitlement/slot reservation, 30-дневную идемпотентность и retention purge. Реальные внешние сервисы не требуются для API-тестов. API для channels, catalog, knowledge base, leads, analytics, диалогов/сообщений, webhook, real-time и billing пока не добавлен: для соответствующих доменов ещё не подготовлены необходимые application services/контракты. Требования и оставшиеся решения см. в `API_CONTRACT.md`.

## 7. Решения, которые ТЗ оставляет открытыми

- ТЗ не задаёт действия SQL `ON DELETE` для всех FK; для реализованных связей они зафиксированы в миграциях. Отдельная политика удаления аккаунта не входит в текущий поток удаления проекта и должна быть определена, если удаление аккаунтов будет добавлено.
- Для customers применяется уникальность `(project_id, channel_type, external_user_id)`. Автоматическое объединение identities между каналами не входит в MVP-1; неподтверждённые контактные значения не являются ключом объединения.
- Версия release уникальна в пределах агента: `(agent_id, version)`; ограничение реализовано миграцией.
- Для задач приложения `background_jobs.project_id` обязателен; общесистемные задачи без проекта не входят в эту схему.
- При замене catalog source старый источник деактивируется, история импортов и товаров сохраняется.
- Срок хранения событий и аудита — 30 дней. Запрос удаления архивирует проект на 30 дней; после этого сначала удаляются Qdrant points, затем проектные записи PostgreSQL.
- Для авторитетного источника каталога используется частичный уникальный индекс по `project_id` при `is_authoritative = true`. Для активных сессий действует ограничение не более одной записи на проект/канал/внешний чат.
- По `usage_records` ТЗ требует индексы, но не уникальность записей по периоду; уникальное ограничение не вводится без отдельного требования.
- Scope биллинговых таблиц определён выше; подробные бизнес-правила и реализация billing API относятся к Части 2.5.

## 8. Runtime authentication flow (JWT principal)

Аутентификация использует существующие `users`, `user_identities` и `account_memberships`; новая таблица или изменение схемы не требуются.

1. Клиент передаёт JWT в `Authorization: Bearer`. Backend проверяет `alg=RS256`, выбирает публичный RSA-ключ по `kid` из `JWT_PUBLIC_KEYS` и валидирует key ring при запуске.
2. Обязательные claims: `iss`, `aud`, `exp`, `nbf`, `iat`, `sub`, `account_id`, `scopes`. `iss` и `aud` сверяются с настройками. `sub` — внешний UUID пользователя Bitrix; `account_id` — canonical backend UUID. `scopes` — массив строк. `iat` не может быть в будущем; `exp - iat` должен быть больше нуля и не превышать настроенный access TTL (1–15 минут, по умолчанию 15).
3. `sub` разрешается только по `(identity_provider='bitrix', external_user_id=sub)` в `user_identities`. Неизвестный или неоднозначный mapping отклоняется; fallback на email/name отсутствует. `account_id` принимается как canonical ID из токена и не разрешается по внешней identity.
4. Для каждой сборки principal backend по `account_id` и найденному `user_id` читает `account_memberships` с `status='active'`. Отсутствие active membership отклоняется; текущая роль берётся из БД, а не из JWT.
5. Результат — principal с `user_id`, `account_id`, актуальной ролью (`owner`/`admin`/`operator`) и scopes. Route-specific scopes проверяются через FastAPI `SecurityScopes`; точные имена scopes задаются вместе с endpoints в Части 4. JWT/identity/membership ошибки не приводят к поиску пользователя по изменяемым данным.

Разрешение identity и чтение membership выполняются в одной транзакции. Существующие таблицы `accounts`, `users`, `user_identities`, `account_identities`, `account_memberships`, `projects`, `project_operators` и `audit_log` при добавлении этого runtime flow не меняются.

## Диалоговые транзакции и аудит

`dialog_sessions` хранит версию состояния в `version`. Ограничения БД проверяют допустимые значения состояния, причины закрытия, lease fence и счётчика повторных открытий. Сессия связана с проектом и каналом; закреплённый `release_id` не меняется при возобновлении.

`chat_messages` содержит `channel_id`, связанный с каналом сессии составным внешним ключом `(project_id, session_id, channel_id)`. Внешний идентификатор сообщения уникален в пределах канала: `(project_id, channel_id, external_message_id)`. Ограничения БД допускают роли `user`, `assistant`, `operator`, `system` и известные статусы доставки; для внутренней заметки используется `not_required`.

`domain_events` хранит события с envelope: тип события, тип и идентификатор агрегата, `tenant_ids`, время возникновения, версию схемы, correlation ID и payload. Записи неизменяемы: обновление и удаление запрещены на уровне БД. События аудируют открытие, возобновление и закрытие сессии, а также фиксацию хода.

`commit_turn` выполняется в одной транзакции: блокирует сессию, проверяет владельца lease и fence, сохраняет сообщения, изменения сессии и версии, событие домена и запись Outbox. Outbox хранит nullable `chat_message_id` с составным FK на исходящее сообщение, чтобы delivery worker мог атомарно обновить его статус. Устаревший fence приводит к ошибке и откату всей транзакции. Системные заметки фиксируются worker-ом под session lease, не создают Outbox и имеют `delivery_status=not_required`. Открытие, закрытие и возобновление сессии также записывают события аудита; возобновление использует ту же закрытую сессию, сохраняет историю и release, увеличивает `reopen_count` и `version`.
