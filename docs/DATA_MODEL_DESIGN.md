# Проект схемы данных: Часть 2

Это проект логической схемы для Части 2 [BACKEND_MVP_TZ.md](./BACKEND_MVP_TZ.md), включая границу биллинга на уровне аккаунта из Части 2.5. ТЗ остаётся главным источником требований. Пункты, помеченные как предложения, — варианты реализации там, где ТЗ не задаёт техническое правило; это не новые требования к поведению продукта.

## 1. Владение данными и изоляция

Иерархия владения: `account -> project -> agent`. Membership, роли и entitlements принадлежат аккаунту. Каналы, настройки агента, каталог, база знаний, клиенты, диалоги, заявки и эскалации принадлежат проекту. Доступ проверяется по JWT scope, членству в аккаунте и связи проекта с этим аккаунтом, как указано в ТЗ и [core-architecture.md](./core-architecture.md).

В каждой таблице с проектными данными хранится обязательный `project_id`, ссылающийся на `projects.id`, в том числе в дочерних записях, у которых проект можно определить через родителя. Каждый запрос проектных данных ограничивается контекстом проекта пользователя. Для ссылок между проектными записями используются составные внешние ключи с `project_id`, чтобы запись не могла ссылаться на родителя из другого проекта. Для таких внешних ключей родительским таблицам потребуются соответствующие уникальные ключи, например `(project_id, id)`.

`projects.account_id` ссылается на `accounts.id`. В аккаунтных записях хранится `account_id`; в записях, которые относятся к проекту, но учитываются или оплачиваются на уровне аккаунта, хранятся оба идентификатора — `account_id` и `project_id`. Предлагаемый способ гарантировать их согласованность — составной внешний ключ на `(projects.id, projects.account_id)`.

`user_id` — столбец будущей таблицы `account_memberships`; он хранит внешний идентификатор пользователя (`subject`) из системы аутентификации. Отдельную таблицу `users` пока не вводим, а внешний ключ для `user_id` не задаём: ТЗ не определяет ни таблицу пользователей, ни конкретную систему аутентификации.

## 2. Сущности и связи

| Сущность или группа | Владение / ключи изоляции | Связи |
|---|---|---|
| `accounts` | Корневая сущность аккаунта | На неё ссылаются `projects` и аккаунтные записи. |
| `account_memberships` | Аккаунт: `account_id` | Каждая запись принадлежит аккаунту. Уникальность membership — внутри аккаунта; роли проверяются сервером. |
| `entitlements` | Аккаунт: `account_id`, одна запись на аккаунт | Вычисленный snapshot/cache прав из тарифа, подписки, доступного баланса и `agent_slots`, с TTL и инвалидацией при изменениях источников. Флаги и квоты отражают эффективные права; таблица не является самостоятельным источником прав. |
| `projects` | Проект принадлежит аккаунту: `account_id` | `account_id -> accounts.id`; индекс по `account_id`. |
| `agents`, `agent_drafts`, `agent_releases` | Проект: `project_id` | Агент принадлежит проекту; draft и неизменяемые releases — агенту в том же проекте. До первой публикации `active_release_id` может быть пустым; иначе он должен указывать на release того же агента. Версия уникальна в пределах агента. Draft хранит изменяемый JSONB `config`; release — неизменяемый JSONB `snapshot` с ключами `prompt`, `tone`, `model_settings`, `sales_rules`, `functions`, `response_settings`. Credentials канала, каталог и база знаний в snapshot не включаются. |
| `channels` | Проект: `project_id` | Канал принадлежит проекту. Идентификатор подключения уникален согласно контракту интеграции. |
| `catalog_sources` | Проект: `project_id` | Источник принадлежит проекту; в MVP-1 допускается не более одного авторитетного источника. При замене старый источник деактивируется, история импортов и товаров сохраняется. |
| `catalog_imports`, `catalog_import_errors` | Проект: `project_id` | Импорт ссылается на источник того же проекта; ошибки импорта принадлежат импорту того же проекта. |
| `products` | Проект: `project_id` | Товар принадлежит источнику каталога и может ссылаться на импорт, в котором его видели в последний раз; все ссылки — в рамках того же проекта. |
| `kb_documents`, `kb_chunks` | Проект: `project_id` | Chunk принадлежит документу того же проекта; идентификаторы vector points относятся к производным данным в Qdrant. |
| `customers`, `customer_identities`, `customer_variables` | Проект: `project_id` | Identity и переменные клиента принадлежат клиенту в том же проекте. Неподтверждённые контактные значения не используются для объединения identity. |
| `chat_sessions`, `chat_messages`, `dialog_variables` | Проект: `project_id` | Сессия связана с проектом, каналом и клиентом этого проекта. Сообщения и переменные диалога принадлежат сессии того же проекта. При возобновлении закрытой сессии сохраняются та же строка и `release_id`. Для `(project_id, channel_id, external_chat_id)` допускается не более одной активной сессии. |
| `tool_executions` | Проект: `project_id` | Ссылается на сессию и, если есть, сообщение того же проекта. Аргументы и результаты редактируются; credentials исключаются. |
| `leads`, `lead_items` | Проект: `project_id` | Заявка ссылается на проект, сессию и клиента; её позиции принадлежат заявке и сохраняют подтверждённый снимок товара. |
| `escalations` | Проект: `project_id` | Ссылается на сессию этого проекта. |
| `inbox` | Проект: `project_id` | Ссылается на канал этого проекта; идентификатор события провайдера уникален в рамках канала. |
| `background_jobs` | Задачи проекта: обязательный `project_id` | Каждая задача приложения относится к проекту; ссылки из payload разрешаются в том же проекте. Общесистемные задачи без проекта в эту схему не входят. |
| `outbox` | Проект: `project_id` | Ссылается на проект и его канал/aggregate. Перед созданием проверяется актуальный session fence. |
| `events`, `audit_log` | Контекстные: `account_id`, а для проектных событий также `project_id` | Проектное событие указывает проект; аккаунтное действие — аккаунт. Требуются индексы по проекту/времени/типу, retention и маскирование ПДн. |
| `llm_calls`, `usage_counters` | Контекст аккаунта и проекта | Для проектного использования хранят `account_id` и `project_id`; нужны индексы для запросов по времени. Credentials провайдера не хранятся. |
| `tariff_plans`, `llm_models`, `dancoin_packages` | Глобальные версионируемые каталоги | На них ссылаются биллинг и учёт использования; они не принадлежат проекту. |
| `subscriptions` | Аккаунт: `account_id` | Ссылается на `accounts` и `tariff_plans`; не более одной текущей подписки на аккаунт; trial выдаётся аккаунту один раз. По окончании оплаченного периода и при ручной отмене платные LLM-вызовы немедленно прекращаются; 7-дневный grace period предназначен только для оплаты/возобновления и сохранения конфигурации, затем аккаунт переходит в `parking`. |
| `dancoin_balances` | Аккаунт: `account_id` | Связь один-к-одному с `accounts`; ledger — источник финансовой истины, баланс — атомарная проекция раздельных грантового/купленного остатков, резервов и долга. Ежедневная сверка восстанавливает проекцию из ledger и активных reservations и создаёт alert; ledger не переписывается. |
| `dancoin_transactions`, `dancoin_reservations` | Аккаунт: `account_id` | Transactions — неизменяемый ledger; reservation указывает аккаунт и операцию/call. Резервирование атомарно проверяется против доступного баланса аккаунта. Исправление проводится компенсирующей записью, а не изменением существующей. Расходование использует гранты первыми; долг от поздней корректировки погашается только купленными Dancoin, начисления покупок сначала закрывают долг, гранты долг не уменьшают. Долг блокирует платные LLM-вызовы. |
| `invoices`, `payments`, `payment_events` | Аккаунт: `account_id` | Invoice принадлежит аккаунту; payment ссылается на invoice того же аккаунта; payment event связан с аккаунтом через payment/invoice. Повторное уведомление дедуплицируется по `provider_event_id`; финансовый эффект имеет отдельную идемпотентность по payment/invoice. Статус платежа подтверждается через provider adapter. |
| `usage_records` | Смешанный scope: `account_id`, `project_id` | Одна неизменяемая запись на биллинговую операцию: `id`, `account_id`, optional `project_id`, `metric`, `quantity`, `unit`, optional token counts, `model_id`, `price_version`, `dancoin_cost NUMERIC(12,2)`, UTC billing period, `occurred_at`, unique `idempotency_key`. Запись проекта относится к аккаунту-владельцу; корректировки — новыми связанными записями. `usage_counters` — агрегаты по периоду/метрике, не взаимозаменяемы с фактами; usage, агрегат и ledger settlement атомарны. |
| `agent_slots` | Проект: `project_id` | Одна запись на проект; лимиты слотов атомарно проверяются и обновляются для проекта. Подписка и баланс Dancoin общие для аккаунта. |

Таким образом, в Части 2.5 есть три scope: глобальные версионируемые каталоги (`tariff_plans`, `llm_models`, `dancoin_packages`), аккаунтные записи подписок/платежей/Dancoin и проектные лимиты агентов с атрибуцией использования. `usage_records` имеют смешанный scope: оплата относится к аккаунту, а `project_id` показывает, в каком проекте возникло использование.

### 2.1. Биллинговые контракты

- **Snapshots:** invoice хранит JSONB snapshot с `schema_version`, типом/кодом и версией элемента каталога, отображаемым именем, ценой и валютой, периодом (если применимо), а для тарифа — features, limits и условия Dancoin-гранта; для пакета — количество Dancoin. Денежные значения сериализуются десятичными строками, не JSON float. При успешной оплате subscription получает неизменяемый snapshot тех же условий на оплаченный период. Новые версии каталогов не изменяют ранее созданные invoice/subscription snapshots.
- **Источники истины:** опубликованные версии каталогов, snapshots invoice/оплаченного периода и неизменяемый Dancoin ledger. `dancoin_balances` — атомарная проекция ledger и активных reservations с раздельными грантовым/купленным остатками, резервами и долгом. `entitlements` — вычисляемый snapshot/cache прав из тарифа, состояния подписки, доступного баланса и `agent_slots`; он не является источником каталожных условий.
- **Транзакционные границы:** ledger-операция и balance-проекция обновляются вместе под блокировкой аккаунта; факты `usage_records`, агрегаты `usage_counters` и ledger settlement фиксируются одной транзакцией. Сетевой LLM-вызов выполняется вне открытой БД-транзакции: reservation фиксируется заранее отдельной транзакцией. Payment event сохраняется в durable inbox до ACK; подтверждённый и идемпотентный финансовый эффект применяется транзакционно. Ежедневная сверка восстанавливает только balance-проекцию по ledger и активным reservations; ledger не редактируется.
- Конкретные цены, валюты, гранты и лимиты остаются продуктовыми данными и не задаются миграциями до утверждения; поля snapshots описывают структуру, но не значения прайса.

### Каталог, клиенты и база знаний

Все новые записи содержат `project_id`. Ссылки между источниками и импортами, импортами и ошибками, источниками и товарами, товарами и последним импортом, клиентами и identities, документами и chunks используют составные внешние ключи с `project_id`.

`catalog_sources.mapping`, `products.attributes` и `customers.profile` — JSONB для гибких структур. Остальные поля, нужные для уникальности, фильтрации и сортировки, хранятся явно. `catalog_sources` допускает один авторитетный источник на проект через частичный уникальный индекс.

Финализация импорта выполняется одной транзакцией: блокирует запись импорта и источника, upsert-ит товары, помечает отсутствующие товары неактивными и обновляет статус импорта. Деактивация разрешена только после полного чтения и обработки файла без структурных ошибок, с безопасным отчётом полноты и без completeness-critical ошибок. При любой ошибке SQL вся транзакция откатывается; некритичные ошибки строк могут завершить импорт со статусом `completed_with_errors`.

`kb_documents` хранит исходный ключ, имя файла, текст (если доступен), версию и статус обработки. `kb_chunks` хранит текстовые фрагменты и внешний `vector_id`; сами embeddings остаются в Qdrant. Уникальность chunk обеспечивается в рамках документа и его версии.

Значения статусов, типы и длины отдельных полей в новых таблицах — решения реализации там, где они не зафиксированы ТЗ; проверяемые им ограничения и индексы описаны в соответствующей Alembic-миграции и интеграционных тестах.

### Прикладные события, доставка и диагностика

`inbox` сохраняет статус очереди, время получения и завершения, безопасную диагностику ошибки и нормализованное событие. Повторная доставка дедуплицируется по `(project_id, channel_id, provider_event_id)`; создание события и фоновой задачи выполняется в транзакции вызывающей стороны.

`background_jobs` хранит приоритет, lease, попытки, следующее время запуска (`available_at`), correlation ID и диагностическую ошибку. Выдача задач использует `FOR UPDATE SKIP LOCKED`; повторные попытки выполняются с ограниченным backoff, а ключ идемпотентности защищает enqueue от дублей. Для внешних вызовов exactly-once не обещается.

`outbox` хранит вид сообщения, destination, aggregate ID, payload, idempotency key, попытки, deadline, следующее время доставки (`available_at`) и причину удержания/неопределённого результата. `enqueue_outbound_message` проверяет актуальный session fence в той же транзакции, что и запись Outbox и durable job. `commit_turn` также проверяет fence перед фиксацией сообщений, событий и Outbox.

`domain_events` — неизменяемый журнал событий; для выборки добавлен индекс по проекту, времени и типу. `tool_executions` ссылается на сессию и, при наличии, сообщение того же проекта. `leads` и `lead_items` используют project-scoped ссылки, уникальный ключ заявки и снимок подтверждённого товара. `escalations` индексируется по проекту, статусу и SLA deadline. `audit_log` содержит account/project context, автора, действие, сущность и очищенный diff. `llm_calls` хранит provider/model/purpose, токены, задержку и код ошибки без provider credentials; `usage_counters` агрегирует метрики по проекту и периоду.

Для JSONB payload и диагностических текстовых полей persistence-слой маскирует распознаваемые credential-поля/значения перед записью. В `domain_events.payload` и `audit_log.diff` дополнительно маскируются распознаваемые адреса email и телефонные номера. Структурированное логирование отдельно редактирует известные секреты. Это не универсальный анализатор секретов/ПДн: новые форматы требуют расширения распознавания. Срок хранения `domain_events` и `audit_log` — 30 дней. Отдельная ежедневная команда (cron/scheduler) удаляет события по `occurred_at` и записи аудита по `created_at`; для `domain_events` разрешено удаление только записей старше 30 дней. Worker не выполняет retention cleanup.
| `chat_sessions` | Частичный уникальный индекс для не более одной активной сессии по `(project_id, channel_id, external_chat_id)`; отдельный индекс для поиска закрытой сессии при возобновлении. Все связанные ID должны относиться к одному проекту. Захват lease атомарно увеличивает `lease_fence`. |
| `chat_messages` | Уникальность внешнего message ID в рамках канала; индекс `(session_id, created_at)`. |
| `inbox` | Уникальность `(project_id, channel_id, provider_event_id)`. |
| `background_jobs` | Индекс выбора задач `(status, available_at, priority)`; credentials исключаются из payload. |
| `outbox` | Уникальный idempotency key; индекс готовых доставок; проверка session fence перед созданием записи. |
| `tool_executions` | Индекс по session/message; credentials и секретные поля исключаются. |
| `leads`, `lead_items` | Уникальный request/idempotency key; в MVP-1 нет CRM remote ID. |

| `events`, `audit_log` | Индексы по проекту, времени и типу; применяются retention и маскирование ПДн. |
| `llm_calls`, `usage_counters` | Индексы по аккаунту, проекту и времени; ключи провайдеров не хранятся. |
| `tariff_plans`, `llm_models`, `dancoin_packages` | Уникальность `(code, version)` или `(model_id, version)`, как указано в ТЗ. Версии, на которые ссылаются оплаченные периоды/usage, сохраняются. |
| `subscriptions` | FK на аккаунт и тарифный план; не более одной текущей подписки на аккаунт; trial выдаётся один раз на аккаунт. |
| `dancoin_balances` | FK один-к-одному на аккаунт. |
| `dancoin_transactions` | Уникальный idempotent reference; индексы по аккаунту и времени. |
| `dancoin_reservations` | Уникальность operation/call ID; атомарное резервирование баланса. |
| `invoices` | Уникальный номер invoice. |
| `payments` | FK на invoice и аккаунт; уникальность `(provider, external_payment_id)`. |
| `payment_events` | Уникальный `provider_event_id` для дедупликации уведомлений; отдельный уникальный ключ бизнес-эффекта по payment/invoice для защиты от повторного начисления. |
| `usage_records` | Индексы по аккаунту, проекту, началу периода и метрике; уникальный idempotency key операции, без уникальности по периоду. |
| `agent_slots` | Уникальный `project_id`; атомарная проверка лимитов проекта. |

Там, где проектная запись ссылается на другую проектную запись, составной внешний ключ должен включать `project_id`. Например, канал и клиент сессии, сессия сообщения, источник товара должны быть из того же проекта. Это защита ссылочной целостности, но не замена проверки авторизации и фильтрации каждого запроса по проекту.

## 4. Архивация и удаление проекта

При запросе удаления проект сразу архивируется. Все данные проекта, включая PostgreSQL-записи и Qdrant points, остаются недоступными для обычной работы и хранятся 30 дней, чтобы tenant мог восстановить проект. Восстановление до окончания срока отменяет ожидающее удаление и возвращает прежний статус проекта.

1. Удаление аккаунта **запрещено (`RESTRICT`)**, пока на него ссылаются проекты, текущие подписки, invoices/payments, ledger или записи с обязательным сроком хранения. Удаление аккаунта — отдельная операция жизненного цикла, а не массовый каскад.
2. При физическом удалении проекта дочерние PostgreSQL-записи удаляются внутренней процедурой в порядке внешних ключей. Текущие project FK используют `RESTRICT`, поэтому порядок очистки проверяется интеграционным тестом.
3. `domain_events`, `audit_log`, `llm_calls` и `usage_counters` хранятся вместе со всем архивом в течение 30 дней и удаляются при окончательном удалении проекта.
4. После 30 дней удаляются Qdrant points из одной конфигурируемой коллекции по фильтру с `project_id` и `object_type` (`kb_chunk` или `product`). Для Qdrant нет SQL FK. Сбой внешней очистки нельзя считать успешным завершением удаления проекта.
5. После 30 дней отдельная ежедневная команда удаляет проектные записи в порядке внешних ключей и корневую запись проекта. Повторный запуск процедуры удаления должен быть безопасным.
6. Диагностические записи `catalog_import_errors` для проектов, не ожидающих удаления, очищаются после 30 дней. Это не удаляет импортированный каталог, продукты или Qdrant points активного проекта.

Порядок очистки принят: сначала Qdrant, затем PostgreSQL. В текущей схеме project FK используют `RESTRICT`; сервис удаляет дочерние строки явно в порядке зависимостей. Восстановление возможно в течение 30 дней; защищённые API endpoints архивации/удаления и восстановления будут реализованы после появления общей авторизации. Команда: `uv run --no-sync python -m ai_seller_core.jobs.project_deletion_scheduler`; она запускается ежедневно через системный scheduler/cron, не через worker.

## 5. Инварианты транзакций и конкурентного доступа

- `commit_turn` — единственная транзакционная точка записи результата диалогового хода: блокировка сессии, проверка владельца lease/fence, затем атомарная запись сообщений, изменений сессии, доменных событий и Outbox. При ошибке проверки все записи откатываются.
- Открытие/возобновление и закрытие сессии выполняются Dialog Worker в отдельных коротких транзакциях с блокировкой и аудитом. Закрытый диалог возобновляется в той же строке, с прежней историей и `release_id`.
- Вызовы LLM, мессенджера, Qdrant и файлового хранилища не выполняются внутри долгих бизнес-транзакций.
- Для фоновых задач используется доставка at-least-once и идемпотентная обработка, с lease/retry-метаданными, `job_id`, `correlation_id` и ограниченной безопасной диагностикой. Exactly-once для внешних HTTP-вызовов не обещается.
- Публикация release блокирует строку агента, проверяет draft, создаёт неизменяемый release и переключает `active_release_id` в одной транзакции. Создание сессии блокирует ту же строку агента на чтение статуса/release и запись сессии. Откат атомарно переключает указатель, не изменяя release.
- Счётчики/лимиты проекта и резервирование аккаунтного баланса изменяются атомарно при конкурентном доступе.

## 6. Текущее состояние реализации

Модели и миграции persistence покрывают аккаунты и проекты, каналы, конфигурации агентов и релизы, диалоги, каталог, клиентов и базу знаний, Inbox/Jobs/Outbox, прикладные сущности, события, аудит, вызовы LLM, счётчики использования и запросы удаления проектов. Проектные связи и ограничения изоляции задаются внешними ключами, включая составные связи с каналом и сессией. Реализация проверок lease/fence, атомарной фиксации хода, идемпотентности и безопасного удаления описана в соответствующих разделах ниже. Наличие persistence-модели не означает, что для каждой сущности уже реализованы публичные API и внешний runtime.

Схема и миграции отражают реализованную persistence-основу. Публичные API, внешние интеграции и отдельные runtime-сценарии могут оставаться задачами последующих частей.

## 7. Решения, которые ТЗ оставляет открытыми

- ТЗ не задаёт действия SQL `ON DELETE` для всех FK; для реализованных связей они зафиксированы в миграциях. Отдельная политика удаления аккаунта не входит в текущий поток удаления проекта и должна быть определена, если удаление аккаунтов будет добавлено.
- Источник `user_id` определён как внешний subject системы аутентификации. Конкретный провайдер и формат его идентификатора будут уточнены вместе с реализацией аутентификации.
- Для customers применяется уникальность `(project_id, channel_type, external_user_id)`. Автоматическое объединение identities между каналами не входит в MVP-1; неподтверждённые контактные значения не являются ключом объединения.
- Версия release уникальна в пределах агента: `(agent_id, version)`; ограничение реализовано миграцией.
- Для задач приложения `background_jobs.project_id` обязателен; общесистемные задачи без проекта не входят в эту схему.
- При замене catalog source старый источник деактивируется, история импортов и товаров сохраняется.
- Срок хранения событий и аудита — 30 дней. Запрос удаления архивирует проект на 30 дней; после этого сначала удаляются Qdrant points, затем проектные записи PostgreSQL.
- Для авторитетного источника каталога используется частичный уникальный индекс по `project_id` при `is_authoritative = true`. Для активных сессий действует ограничение не более одной записи на проект/канал/внешний чат.
- По `usage_records` ТЗ требует индексы, но не уникальность записей по периоду; уникальное ограничение не вводится без отдельного требования.
- Scope биллинговых таблиц определён выше; подробные бизнес-правила и реализация billing API относятся к Части 2.5.
## Диалоговые транзакции и аудит

`dialog_sessions` хранит версию состояния в `version`. Ограничения БД проверяют допустимые значения состояния, причины закрытия, lease fence и счётчика повторных открытий. Сессия связана с проектом и каналом; закреплённый `release_id` не меняется при возобновлении.

`chat_messages` содержит `channel_id`, связанный с каналом сессии составным внешним ключом `(project_id, session_id, channel_id)`. Внешний идентификатор сообщения уникален в пределах канала: `(project_id, channel_id, external_message_id)`. Ограничения БД допускают только роли `user`/`assistant` и известные статусы доставки.

`domain_events` хранит события с envelope: тип события, тип и идентификатор агрегата, `tenant_ids`, время возникновения, версию схемы, correlation ID и payload. Записи неизменяемы: обновление и удаление запрещены на уровне БД. События аудируют открытие, возобновление и закрытие сессии, а также фиксацию хода.

`commit_turn` выполняется в одной транзакции: блокирует сессию, проверяет владельца lease и fence, сохраняет сообщения, изменения сессии и версии, событие домена и запись Outbox. Устаревший fence приводит к ошибке и откату всей транзакции. Открытие, закрытие и возобновление сессии также записывают события аудита; возобновление использует ту же закрытую сессию, сохраняет историю и release, увеличивает `reopen_count` и `version`.
